oh-my-mlip: Machine-Learning Interatomic Potentials on HPC¶

Machine-learning interatomic potentials (MLIPs) can approach the accuracy of density functional theory (DFT) at a much lower cost, and many pretrained “foundation” models are now available. Installing and running them side by side is still hard: each framework needs its own PyTorch or TensorFlow, CUDA build and accelerated kernels, and a wrong setup can silently run on the CPU or with the wrong model.

oh-my-mlip is an open-source hub that brings the major MLIP frameworks into one registry, installs each in its own conda environment built from a recipe, and counts a model as installed only after it computes energies and forces on the GPU. It can be driven by LLM coding agents such as Claude Code and Codex, and every step also runs from the command line.

This lesson accompanies the two-part ENCCS webinar series. Part 1 covers installing, running and benchmarking MLIPs. Part 2 covers fine-tuning and distillation. Each webinar takes one hour; the times below are for working through the material on your own.

Prerequisites

  • A Linux x86-64 machine or cluster with an NVIDIA GPU

  • conda or mamba on your PATH

  • Basic familiarity with Linux, Python and the command line

  • For Part 2: basic familiarity with molecular dynamics (MD)

See Setup for details.

Get the hub¶

The hub is a git repository. Environments and local records live inside it. Weights live in each framework’s own cache (for example ~/.cache/mace or ~/.cache/huggingface) or, for some models, under models/ in the hub.

git clone https://github.com/JinukMoon/oh-my-mlip.git
cd oh-my-mlip
source env.sh

env.sh sets the cache and CUDA environment variables the scripts expect. Source it in every new shell before running anything.

/plugin marketplace add JinukMoon/oh-my-mlip

Why installing MLIPs is hard¶

Questions

  • Why can’t I install all MLIP frameworks in one environment?

  • What can go wrong without any error message?

  • What does oh-my-mlip do about it?

Objectives

  • Name the main sources of MLIP installation failures

  • Understand the three ideas behind oh-my-mlip: one registry, isolated environments, and verification on the GPU

One environment cannot hold them all¶

Most MLIP frameworks are built on PyTorch (one, GRACE, on TensorFlow), but each release pins its own versions of the deep-learning framework, CUDA and helper libraries. Many also need accelerated kernels compiled for a specific GPU architecture. Installing two frameworks into one environment usually means one of them silently gets a version it was never tested with.

Typical problems:

  • Conflicting PyTorch or CUDA versions between frameworks

  • Kernels compiled for a different GPU architecture than the one you run on

  • NVIDIA drivers too old for the CUDA build in the environment

  • Weights that must be downloaded from different places, some of them gated behind a license agreement

Silent errors are worse than crashes¶

A crash at least tells you something is wrong. The dangerous cases finish without an error:

  • The model runs on the CPU instead of the GPU. With an NVIDIA driver older than the environment’s CUDA build, a few models still run, much more slowly, while most refuse to load.

  • The wrong checkpoint is loaded, for example a different model size or version.

  • A multi-head model computes with a different head than the one you asked for. For example, mace-torch only printed a warning for an unknown head name and computed with another head. oh-my-mlip stops with an error when the head actually used differs from the one requested.

What oh-my-mlip does¶

  1. One registry. models.json lists every supported model with its environment recipe, where its weights come from, and the exact lines that create the ASE calculator.

  2. Isolated environments with recorded builds. Each framework gets its own conda environment, built from a recipe. Every verified build is recorded in a lock file, so the same package set can be replayed exactly.

  3. Verification on the GPU. A model counts as installed only after it has computed energies and forces on the GPU. A clean exit of the install script is not enough.

The upstream frameworks are run as they are. oh-my-mlip does not reimplement any model.

Discussion

Have you ever had an MLIP run “successfully” but much slower than expected, or with results that did not match a colleague’s? What turned out to be the cause?

Keypoints

  • MLIP frameworks need conflicting software stacks, so each one gets its own environment.

  • The worst failures are silent: CPU fallback, wrong checkpoint, wrong head.

  • oh-my-mlip treats “computes energies and forces on the GPU” as the definition of installed.

Install and verify a model¶

Questions

  • How do I install an MLIP framework with oh-my-mlip?

  • How do I know the installation really works?

Objectives

  • Install one framework and verify a model on the GPU

  • Read the verification result

  • Install a gated model

Ask your agent¶

Install MACE and check it runs on my GPU.

The agent installs the environment, compiles what your GPU needs, and reports the model only once it has computed energies and forces there.

Or run it yourself¶

From the hub directory, after source env.sh:

./install.sh MACE                      # a framework name or an env name
./install.sh MACE SevenNet ORB         # several at once
./install.sh --dry-run MACE            # print the plan, install nothing
./install.sh --status MACE             # ready / partial / broken / not installed

install.sh runs the same steps every time: create the environment from its recipe, install CatBench, prepare the weights, compile what must be compiled for your GPU, and mark the environment ready.

If an install is interrupted, run it again: an environment whose imports work is kept and finished. If they fail, it stops without deleting anything, and ./install.sh --rebuild <env> deletes that environment and builds it again.

Verify on the GPU¶

python scripts/setup_verify.py MACE-MPA-0 --json

The result is one JSON verdict. The model is GPU-verified only if it computed energies and forces on the GPU. If the verdict says degraded: true and device: cpu, the NVIDIA driver is older than the environment’s CUDA build: the model is not ready (see Troubleshooting and cleanup).

Replay a verified build exactly¶

Every verified build is recorded in envs/locks/. To install exactly that package set, with no dependency resolution:

OMM_USE_LOCK=1 ./install.sh MACE

Gated models¶

UMA and eSEN weights are gated. Accept the license on the model’s Hugging Face page with your account, then log in from your own terminal before installing:

hf auth login

An agent should never ask you to paste a token into the chat.

Use a model in your own work¶

Questions

  • How do I use an installed model in my own script?

  • How can I compare several models quickly?

Objectives

  • Get the calculator lines and the interpreter for a model with resolve()

  • Relax a structure with an MLIP

  • Compare models from one script

Every framework lives in its own environment, so a model always runs under that environment’s Python interpreter.

Ask your agent¶

Relax POSCAR with MACE-MPA-0 and give me the relaxed structure.

Write an MD script for this slab that uses SevenNet.

The agent takes the calculator lines from the registry and runs your script with the right interpreter.

In your own script: resolve()¶

Use this for MD, relaxations and anything long. Copy the lines once; your script does not need oh-my-mlip at run time.

import sys; sys.path.insert(0, "<path to the hub>")
from oh_my_mlip import resolve

spec = resolve("MACE")        # a family, or a version such as "MACE-MH-1-OMAT"
print(spec["python"])         # the interpreter to run your script with
print(spec["imports"])        # import lines
print(spec["inference"])      # the line that creates `calc`
print(spec["env_run"])        # environment variables to export first (often empty)

Export the variables in env_run, paste imports and inference into your script as they are, then run it with spec["python"]:

# my_run.py  ->  run with spec["python"]
from ase.io import read
from mace.calculators import mace_mp

atoms = read("POSCAR")
calc = mace_mp(model='medium-mpa-0', dispersion=False, default_dtype='float64', device='cuda')
atoms.calc = calc
print(atoms.get_potential_energy())

Across models from one script¶

For quick comparisons, each model runs in its own environment process, so the calling Python needs no model installed:

import oh_my_mlip

out = oh_my_mlip.run("MACE", atoms)          # {"energy": ..., "forces": ...}

with oh_my_mlip.WorkerPool() as pool:        # workers stay alive between calls
    for name in ("MACE", "SevenNet"):
        resp = pool.request(name, atoms)
        print(name, resp["results"]["energy"])

Every call crosses a process boundary, so use resolve() for MD loops.

D3 dispersion¶

out = oh_my_mlip.run("MACE", atoms, apply_d3=True)

or, inside the model’s environment:

from catbench.dispersion import DispersionCorrection
calc = DispersionCorrection().apply(calc)

Running on GPU clusters¶

Questions

  • What changes when I move from a workstation to a Slurm cluster?

  • How do I prepare jobs instead of running them directly?

Objectives

  • Know which steps depend on the GPU you install on

  • Write Slurm job scripts for CatBench and fine-tuning without submitting them

Install where you will compute¶

Some frameworks compile kernels for the GPU they are installed on (NequIP and SevenNet with OpenEquivariance, Allegro with CuEquivariance, and the D3 kernel). Verification also needs a GPU. On a cluster, run the installation inside a GPU job or an interactive GPU session, on the same kind of GPU you will use for production.

To prepare NequIP or Allegro jobs for a different GPU architecture, pass it explicitly, for example:

resolve("NequIP", arch="sm86")

Things to check on a cluster¶

  • Internet access. Compute nodes often have none. Weights must be fetched where the network works, before the jobs start.

  • Disk. About 5 to 15 GB per model. Put the hub on a filesystem that compute nodes can read, with enough quota.

  • Drivers. Each environment pins its own CUDA build; check that the cluster’s NVIDIA driver is new enough for the models you need.

  • Speed tests. Keep benchmark output on fast local storage. Writing every step to a slow network filesystem can make a model look slower than it is.

Write job scripts, submit yourself¶

The CatBench and fine-tuning tools can write Slurm scripts without running them:

python run_examples/catbench_quickstart.py MamunHighT2019 --only MACE \
    --slurm --emit-only --partition <partition>
python scripts/ft_run.py MACE --dataset frames.traj --out ft_mace \
    --slurm --partition <partition>

The generated header sets only the job name, partition, log files, one task and one GPU. Wall time, memory, CPUs and account are left to your cluster’s defaults, so add them before submitting if those defaults do not suit.

Discussion

On your cluster, where would you keep the hub: in your home directory, on a project filesystem, or on scratch? What are the trade-offs?

Keypoints

  • Install and verify on the same kind of GPU you will run on.

  • Fetch weights where the network works; compute nodes often have no internet.

  • Let the tools write job scripts, then add your cluster’s resources and submit.

Benchmark MLIPs with CatBench¶

Questions

  • How well do different MLIPs reproduce DFT adsorption energies?

  • How can I benchmark models on my own DFT data?

Objectives

  • Run a small CatBench benchmark and read its report

  • Turn your own VASP calculations into a CatBench dataset

CatBench benchmarks MLIPs on adsorption energies in heterogeneous catalysis. It is installed in every oh-my-mlip environment.

Ask your agent¶

Benchmark MACE, SevenNet and UMA on adsorption energies for CO2 reduction on Cu, with D3.

The agent asks which dataset (or recommends a published one), which models, whether to add D3, and whether this is a new benchmark or a rerun.

Or run it yourself¶

A first run, 20 small-adsorbate reactions with one model, takes a few minutes:

mkdir my_benchmark && cd my_benchmark
python <hub>/run_examples/catbench_quickstart.py MamunHighT2019 --only MACE --max-reactions 20
python <hub>/scripts/catbench_report.py --result ./result --out ./report

You get:

  • jobs/: one rerunnable job script per model

  • result/: CatBench results for every model

  • report/: the MAE table and plot, and an analysis workbook

Option

Effect

--only MACE,SevenNet

frameworks to run

--max-reactions N

only the first N reactions (the report marks it as a subset)

--d3

add D3 dispersion

--calc-num N

calculator instances per model (use 1 for large models on a small GPU)

--slurm --emit-only --partition <p>

write Slurm scripts without running them

List the available datasets with:

python3 <hub>/scripts/catbench_datasets.py --list

For a benchmark you will report, pin the CatBench version with --catbench-version and pass --expect-models to the report, so that a missing model is caught.

A small file of large molecules can take hours, so try a subset first.

Your own VASP data¶

Lay out finished calculations, each with a CONTCAR and an OSZICAR:

my_dataset/
├── Pt111/          # one directory per surface
│   ├── slab/       # the clean slab
│   ├── H/          # one directory per adsorbate
│   └── OH/
└── gas/
    ├── H2gas/      # one directory per gas reference
    └── H2Ogas/

Then ask:

Turn my VASP calculations in ./my_dataset into a CatBench dataset called my_dataset.

The agent proposes the reaction coefficients (for example, H = adslab - slab - 1/2 H2) and asks you to confirm them. The conversion runs on a copy; your original files are hashed before and checked after.

Without an agent, from the hub directory:

# 1. scan: complete and incomplete pairs, proposed coefficients
python3 scripts/catbench_vasp_stage.py scan --source my_dataset --out stage

# 2. confirm coefficients in a file outside stage/, e.g. coeff_setting.json:
#    {"H":  {"slab": -1, "adslab": 1, "H2gas": -0.5},
#     "OH": {"slab": -1, "adslab": 1, "H2Ogas": -1, "H2gas": 0.5}}

# 3. stage: copy what CatBench reads and write the runner
python3 scripts/catbench_vasp_stage.py stage --source my_dataset --dest stage \
    --dataset-name my_dataset --coeff coeff_setting.json --python <env>/bin/python

# 4. convert on the copy
sh stage/run_stage.sh

# 5. verify the originals and the JSON
python3 scripts/catbench_vasp_stage.py verify --source my_dataset --dest stage
<env>/bin/python scripts/catbench_datasets.py --check stage/raw_data/my_dataset_adsorption.json

<env>/bin/python is the interpreter of any installed environment; every environment has CatBench.

Fine-tune a pretrained model¶

Questions

  • When is fine-tuning a pretrained MLIP worth it?

  • How do I fine-tune different frameworks without learning each trainer?

Objectives

  • Prepare a DFT dataset for fine-tuning

  • Inspect the settings a framework really has

  • Fine-tune a model and check that the result reloads and runs

Starting with Part 2?

You need the hub (Setup) and one GPU-verified model (Install and verify a model).

Pretrained models are trained on large, general datasets. For a specific system, such as one catalyst surface or one electrolyte, fine-tuning on your own DFT data can improve accuracy where it matters for you.

One workflow, each framework’s own trainer¶

Every framework fine-tunes differently: MACE takes command-line flags, NequIP and SevenNet read YAML configs, DeePMD reads input.json, and each expects its own dataset layout. oh-my-mlip converts your data to that framework’s format, writes the framework’s own config and command, and runs the upstream trainer. Nothing is reimplemented.

Which models can be fine-tuned is listed in Fine-tuning per framework.

Ask your agent¶

Fine-tune MACE on frames.traj - just a quick check that fine-tuning works.

Fine-tune SevenNet-MF-OMPA on my DFT frames for 100 epochs.

The agent first reads which settings the framework really has (DeePMD counts steps instead of epochs, not every trainer has EMA or early stopping), then asks for the exact variant, the training length, batch size, learning rate and loss weights, and the output directory. Every value comes from you, from the framework’s official fine-tuning example, or from its upstream default, and the run records which one it was.

Or run it yourself¶

python scripts/ft_run.py MACE --show-settings      # the settings this framework has
python scripts/ft_run.py MACE --dataset frames.traj --out ft_mace --epochs 50 --seed 0
python scripts/ft_verify.py ft_mace/<checkpoint> --model MACE --json

Option

Effect

--show-settings

list native settings, their defaults and official fine-tuning values

--epochs, --max-steps, --batch-size, --lr

training length, batch size, learning rate

--energy-weight, --force-weight, --stress-weight

loss weights

--version MACE-MH-1-OMAT

start from a specific checkpoint

--emit-only

write the dataset, config and command without running

--slurm --partition <p>

also write a Slurm script (nothing is submitted)

Good practice¶

  • Split by what you want to test. If the question is “does the model work for a composition it has not seen?”, hold out whole compositions, not random frames.

  • Keep the gas references. If you compute reaction energies, include the gas molecules in the training data, because the model’s own gas energies enter every reaction energy.

  • Compare with the same budget. When comparing frameworks, give each the same GPU time or number of steps, and report the official defaults separately.

  • Check the license. A model fine-tuned from a non-commercial checkpoint inherits its terms.

Exercises¶

Exercise 1: read the settings

Run --show-settings for two frameworks. Which settings does one have that the other does not?

Exercise 2: a short fine-tuning run

Fine-tune MACE on a small dataset for a few epochs, then verify the checkpoint. Use your own DFT frames, or make a toy dataset with ASE’s EMT potential. Toy data only exercises the pipeline; it says nothing about accuracy.

Solution

PY=$(python -c 'from oh_my_mlip import resolve; print(resolve("MACE")["python"])')
"$PY" - <<'EOF'
from ase.build import bulk
from ase.calculators.emt import EMT
from ase.io import write
frames = []
for i in range(40):
    atoms = bulk("Cu", "fcc", a=3.6, cubic=True).repeat(2)
    atoms.rattle(0.05, seed=i)
    atoms.calc = EMT()
    atoms.get_potential_energy(); atoms.get_forces()
    frames.append(atoms)
write("frames.extxyz", frames)
EOF
python scripts/ft_run.py MACE --dataset frames.extxyz --out ft_mace --epochs 5 --seed 0
python scripts/ft_verify.py ft_mace/<checkpoint> --model MACE --json

<checkpoint> is the checkpoint file in the output directory; ft_run.json there records what was run.

Keypoints

  • ft_run.py drives each framework’s own trainer behind one interface.

  • Look at the real settings first; frameworks differ.

  • Design the train and test split around the question you want to answer.

Distill a tailored MLIP¶

Questions

  • How can I run long or large MD when a foundation model is too slow?

  • How does distillation make a small model that is accurate for my system?

Objectives

  • Explain the teacher-student idea and on-the-fly active learning

  • Set up a distillation run from an installed model

  • Know what the current engine fixes and what it lets you choose

Teacher and student¶

Large foundation models are accurate across chemistry, but they need GPUs and are slow for long or large MD. Distillation trains a small, fast student to reproduce a large teacher on the structures that matter for your simulation.

In oh-my-mlip, the student is an NN-MTP potential. It has a LAMMPS pair style (nnmtp), so the student runs MD on CPU nodes with no Python or LibTorch at run time. Any installed model can be the teacher.

The loop is on-the-fly active learning, run by the onthefly-distill engine:

  1. The teacher labels a pool of structures (energies and forces).

  2. The student is trained on the pool.

  3. The student runs MD in LAMMPS.

  4. Where the student breaks down, the teacher labels those structures and they are added to the pool.

  5. Repeat until the student stays stable for the MD length you need.

The result is a tailored MLIP for your own system: small, fast, and accurate where it matters for your simulations.

Splitting GPU and CPU work¶

Step

Where it runs

Teacher labels

GPU (the foundation model)

Student training

GPU

Student MD and production runs

CPU nodes, in LAMMPS

This split is useful on HPC: a small GPU allocation builds the student, and the long production MD runs on CPU partitions.

Ask your agent¶

Distill UMA-s-1p2-OMAT into an NN-MTP student for 300 K NVT MD of slab.vasp.

The agent asks for the teacher, how long the student must stay stable, whether this is a quick trial or a production run with accuracy targets, and where LAMMPS and the engine are.

Or run it yourself¶

From the hub directory:

HUB=$PWD
PY=$(python3 -c "import oh_my_mlip; print(oh_my_mlip.resolve('MACE-MPA-0')['python'])")
git clone https://github.com/JinukMoon/onthefly-distill.git ../onthefly-distill   # once
scripts/build_lammps_nnmtp.sh --repo ../onthefly-distill                            # once
"$PY" scripts/distill_bootstrap.py --teacher MACE-MPA-0 --structure slab.vasp \
    --work ./distill --repo ../onthefly-distill --lmp-bin <lmp>
cd distill && sh run_distill.sh > distill.log 2>&1

<lmp> is the LAMMPS binary with the NN-MTP pair style. This quick run only exercises the loop; it says nothing about the student’s accuracy.

For a student you will actually use, run in production mode with explicit targets (values in < > are yours to choose), again from the hub directory:

cd "$HUB"
"$PY" "$HUB/scripts/distill_bootstrap.py" --teacher MACE-MPA-0 --structure slab.vasp \
    --work ./distill_prod --repo ../onthefly-distill --lmp-bin <lmp> \
    --acceptance --mode production \
    --energy-mae-max <meV/atom> --force-mae-max <meV/A> \
    --target-ps <stable MD length, ps> --max-iter <AL rounds> --no-progress-limit <rounds>

and check the verdict, which needs both held-out accuracy and a stable LAMMPS run:

"$PY" "$HUB/scripts/distill_verify.py" --work ./distill_prod --json

Held-out frames you supply with --heldout-file must lie within the compositions the pool spans.

What the current engine fixes¶

Know these before you plan a run:

  • At most four chemical elements in the structure.

  • Student MD uses a Langevin thermostat at 300 K (NVT-like). Another temperature or ensemble is not an option of the current engine.

  • Boundaries: the input must be fully periodic (a slab keeps its vacuum inside the cell); student MD runs with reflecting walls along z.

  • Frozen atoms (FixAtoms) are labelled with the teacher’s forces but not trained on.

  • Several compositions: if the student must work for different compositions (for example, a slab with different numbers of water molecules), seed the pool with all of them. One composition alone fixes only its own total energy.

Accuracy is relative to the teacher

A student learns to reproduce its teacher on your system. It is not more accurate than the teacher, and it is only reliable within the kinds of structures it was trained on. Always check held-out errors against the teacher.

Exercises¶

Exercise 1: plan a distillation

For a system from your own research, decide: which teacher, which structures to seed the pool with, how long the student must stay stable, and which held-out frames you will use to check it.

Exercise 2: a quick trial

Run a quick trial distillation with an installed teacher on a small copper slab. How many rounds did the loop need?

Solution

Make the slab with the teacher’s interpreter, fixing the two bottom layers:

"$PY" - <<'EOF'
from ase.build import fcc111
from ase.constraints import FixAtoms
slab = fcc111("Cu", size=(3, 3, 4), vacuum=10.0, periodic=True)
slab.set_constraint(FixAtoms(indices=[a.index for a in slab if a.tag >= 3]))
slab.write("slab.vasp", format="vasp")
EOF

Then run the quick commands above and count the rounds in distill/distill.log.

Outlook: reactive systems¶

Distilling reactive systems, where bonds break and form, is harder: the pool must contain the reactive events themselves, not only configurations near equilibrium. This is ongoing work and is discussed in the webinar.

Keypoints

  • Distillation turns a large teacher into a small, fast student tailored to your system.

  • Active learning adds teacher labels exactly where the student fails.

  • Teacher work runs on GPUs; the student’s production MD runs on CPU nodes.

A common path:

  1. Benchmark several pretrained models on data close to your problem (CatBench, Part 1).

  2. Fine-tune the best one if its errors matter for your conclusions.

  3. Distill the result into a student when you need long or large MD.

Discussion

For your current project, where would you stop on this path, and what would convince you to go one step further?

Keypoints

  • Start from benchmarks on data close to your problem.

  • Fine-tune for accuracy; distill for speed.

  • Always check the final model against held-out reference data.

Troubleshooting and cleanup¶

Objectives

  • Find out what state your installation is in

  • Fix the most common problems

  • Free disk space and report a problem

Check the state¶

From the hub directory:

python3 scripts/setup_survey.py --table              # every env: ready / partial / missing, gated models, disk
./install.sh --status mace                           # one env's install state; changes nothing
python3 scripts/setup_verify.py MACE-MPA-0 --json    # energies and forces on the GPU

Or ask your agent:

setup_verify failed for NequIP-OAM-L. Find out why and fix it.

Common problems¶

Symptom

Cause

Fix

An install was interrupted, or an env is partial

The build stopped midway

Run ./install.sh <env> again. If its imports fail, it stops without deleting anything; ./install.sh --rebuild <env> deletes the env and builds it again

setup_verify passes with degraded: true, device: cpu

The NVIDIA driver is older than the env’s CUDA build

Upgrade the driver; see the host requirements

HTTP 401 or 403 when downloading UMA or eSEN

License not accepted, or the token belongs to another account

Accept the license on Hugging Face and run hf auth login

EOFError: Ran out of input or “… does not exist” when a model loads

An empty or partial weight file from an interrupted download

Remove the leftovers under models/<framework>/ and run again

NequIP or Allegro fails to load on a different GPU

The compiled model is for another GPU architecture

Compile for this GPU; see Accelerators

pip times out on pypi.nvidia.com

That host is unreachable from your network

python3 scripts/install_nvidia_wheels.py <env>, then ./install.sh <env> again

D3 is unavailable

No nvcc (CUDA toolkit)

Install a CUDA toolkit and run install.sh again; the models themselves still run

Loading UMA-m-1p1-* ends without an error message (exit code 137)

The checkpoint does not fit in host RAM

Use a machine with 32 GB of RAM or more, or a UMA-s-* model

Free disk space¶

conda env remove -p "$OH_MY_MLIP_HOME/envs/<env>"    # an env built by install.sh
python3 scripts/adopt_env.py --remove <env>          # an env you adopted: removes only the registration

Weights live outside the environments: in each framework’s own cache (for example ~/.cache/fairchem, ~/.cache/mace, ~/.cache/huggingface) and, for some models, under models/ in the hub. Delete those directories to reclaim their space; they are downloaded or compiled again when needed.

Report a problem¶

Open an issue at https://github.com/JinukMoon/oh-my-mlip/issues and include:

  • the command or request, and the full error output

  • python3 scripts/setup_verify.py <model> --json for the model involved

  • nvidia-smi and ./install.sh --status <env>

Never include a Hugging Face token or other credentials.

Learning outcomes¶

This material is for computational chemists and materials scientists who want to use MLIPs, for HPC support staff who install MLIP software for users, and for anyone curious about how LLM agents can handle the setup of scientific software.

By the end of this lesson, learners should be able to:

  • Install an MLIP framework in an isolated environment and confirm that the model computes energies and forces on the GPU

  • Get a ready-to-use ASE calculator for a supported model and run it in their own scripts

  • Let an LLM agent do the setup, and check its work

  • Prepare MLIP jobs for a Slurm GPU cluster

  • Benchmark several MLIPs on adsorption energies with CatBench, including their own VASP data

  • Fine-tune a pretrained model on their own DFT data with the framework’s own trainer

  • Distill a large model into a small, fast student that runs MD in LAMMPS on CPU nodes

Current scope¶

The oh-my-mlip recipes and lock files are built for Linux x86-64 (linux-64 packages) with NVIDIA GPUs. Arm-based nodes (such as GH200) and AMD GPUs have not been tested and are not supported yet.
